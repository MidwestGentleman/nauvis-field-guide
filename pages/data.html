How this site stays current

Most of this guide writes itself. Every class, spell, mob, item, recipe, biome and dungeon on these pages is read from the game's own public files when the page loads, so a game update shows up here without anyone editing a page.

The game content also lives on chain: every item, mob, spell, recipe, world and dungeon is a shared object under one content registry. A check on 29 October 2026 found the chain copy and the repo files identical for all 68 mobs. The repo files are much quicker to read, so the site uses them and treats the chain as the authority.

How it works

  1. Find the release

    The browser asks GitHub for the game's latest release tag. The development branch can run ahead of what's live, so the site never reads it unless the release lookup fails.

  2. Read the content files

    It fetches about a dozen files from raw.githubusercontent.com, which allows cross-site reads. The site parses five small TypeScript files as text and never runs them.

  3. Check the shape

    If a file is missing a field the site relies on, loading stops with an "upstream schema changed" message instead of showing wrong numbers.

  4. Cross-reference

    It works out who drops what, where each mob spawns, which recipes use an item, and each class's elements.

  5. Go live where it's cheap

    Small widgets read Sui mainnet directly through its public GraphQL endpoint. Reads only; nothing is ever signed.

Why the game files aren't copied here

The AresRPG repository is source-available, not open source, and its licence forbids redistributing its files. This site's repository therefore contains no game files, pictures included. The minimap views on the map page are the only stored pictures: renders this guide made, like screenshots. Your browser reads the data and loads the art directly from the official repository, and the hand-written pages only state facts and formulas in our own words. An optional script, scripts/build-data.mjs, writes a local cache for offline work; that cache is git-ignored and must not be published.

What could be added live

All of these were tested read-only against mainnet:

  • Character stats and leaderboards by level or XP: all characters can be read in a few GraphQL calls.
  • Recent fights and dungeon clears: from on-chain events.
  • A "game data changed" banner: compare the content registry's revision number in one small request.
  • Market prices: possible, but a full scan of every kiosk takes hundreds of calls. That belongs in a scheduled job that publishes a snapshot, not in every visitor's browser.

What can't be read automatically

  • Strategy: builds, walkthroughs and "is it worth it" can't be read from data, and this guide leaves them out.
  • Official leaderboards and presence: they sit behind the game server's signed-in connection.
  • Gas prices per action: they come from the network, not the game, so the numbers here are observed examples.
  • Formulas: they live in contract code, not data, so the hand-written formula pages carry a "checked" date.

Maintenance checklist

  • When the game ships a release, open the site. If it loads, the data pages are current.
  • If it shows "upstream schema changed", update assets/source.js to the new file shape.
  • Skim the hand-written pages when patch notes mention crafting, fights, gathering or dungeons.
